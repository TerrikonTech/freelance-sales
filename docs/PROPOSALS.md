# Генерация откликов FL.ru

## Цель

Отклик должен за первые 150–200 символов показать, что исполнитель понял
конкретный проект, умеет снять главный риск и предлагает простой следующий
шаг. Генератор не пересказывает бриф и не компенсирует отсутствие опыта
техническими терминами.

## Конвейер

1. Анализ лида выделяет цель, scope, будущие функции, риски, цену и срок.
2. `draft_strategy` выбирает угол, две уникальные детали, микро-план,
   критерий приёмки, одно доказательство и один вопрос.
3. `draft_candidates` создаёт три варианта с разными типами хука.
4. `draft_review` выбирает или полностью переписывает лучший вариант.
5. TypeScript-валидатор повторно проверяет длину, структуру, коммерческие поля,
   ссылку на кейс, технологический фит и отсутствие шаблонных фраз.
6. Если редакторская попытка всё равно не проходит правила, черновик не
   сохраняется как готовый.

## Технологический фит

Явно названная CMS или мобильная технология — отдельное требование, а не ещё
одно слово из брифа. Сейчас детерминированно распознаются 1С-Битрикс, Bitrix24,
WordPress, WooCommerce, Tilda, OpenCart, MODX, Shopify, Webflow, Flutter и
React Native.

Доказательством считаются только:

- точная запись в публичном профиле продавца;
- реальный кейс портфолио, в названии или описании которого указана технология.

Общие 6 лет опыта, работа в Яндексе, знание терминов «инфоблок», «компонент» или
«редакция» не доказывают опыт с 1С-Битрикс. Если доказательства нет:

- `technology_fit.risk` получает значение `elevated`;
- в metadata черновика записывается `technology_fit_unverified`;
- Dashboard показывает предупреждение владельцу;
- локальная проверка блокирует заявления «работал», «делал», «есть опыт»,
  «владею» или «знаю» рядом с неподтверждённой технологией;
- соседний кейс разрешено использовать только как доказательство совпадающей
  продуктовой механики, а не требуемого стека.

Если точное доказательство есть, отклик обязан использовать одно такое
доказательство: ссылку на соответствующий кейс либо подтверждённую запись
профиля.

## Цена, срок и доступность

Цена и срок обязательны в теле отклика и должны совпадать с числовыми полями
FL.ru. Дата старта берётся только из `seller_profile.available_from` (поле
«Когда могу начать» в настройках).

Если дата не заполнена, модель не имеет права придумывать «свободен с…» и больше
не вставляет заглушку «после согласования объёма и получения доступов».
Черновик получает флаг `availability_missing`, а Dashboard просит владельца
указать доступность до отправки. Это намеренная честная деградация: отсутствие
сигнала видно владельцу, но не превращается в ложное обещание клиенту.

## Итоговый чек-лист

- 60–120 слов для `compact`, 100–200 для `standard`, 170–260 для `premium`;
- не более трёх коротких абзацев;
- две детали конкретного заказа без пересказа списка функций;
- один из пяти типов хука и одна из пяти формулировок приёмки;
- микро-план из 2–3 шагов и измеримый результат;
- ровно один релевантный кейс и одна точная ссылка, если кейс найден;
- цена, срок и только подтверждённая доступность;
- ровно один вопрос в финале;
- отсутствие неподтверждённых технологических заявлений, заглушек, давления,
  многоточий и формулы «лучше X, иначе Y».

## Безопасная проверка

Целевые модульные тесты:

```bash
npm test -w apps/api -- --runInBand proposal-quality.spec.ts portfolio-link.spec.ts
```

Живую проверку выполняют созданием одного `pending`-черновика. Его нельзя
одобрять: нужно сверить metadata, убедиться, что доставка отсутствует, и только
после этого показать владельцу текст в Dashboard.
