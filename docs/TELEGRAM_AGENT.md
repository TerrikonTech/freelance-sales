# Telegram-бот и агент общения

## Четыре разных контура

Под словом «бот» в системе скрыты четыре связанные части:

1. управляющий бот получает команды владельца обычным русским языком;
2. Telegram Business webhook принимает сообщения клиентов;
3. owner-session bridge отправляет из личной сессии, когда Business API не
   имеет доступа к конкретному peer;
4. Hermes/Codex классифицирует намерение, готовит текст и обновляет память
   сделки.

Управляющий бот не является произвольным терминалом. Он выполняет только
разрешённые действия, описанные схемой `OwnerIntent`.

## Как разбирается команда владельца

Сначала применяются быстрые детерминированные правила. Они распознают частые
команды без AI: выбор клиента, список клиентов, обзор, создание/отправка
сообщения, подтверждение последнего черновика, ТЗ, дизайн и миссии.

Если правило не подошло, создаётся AI-задача `owner_intent`. Допустимые intent:

| Intent | Что делает |
|---|---|
| `draft_message` | готовит черновик и показывает владельцу |
| `send_message` | готовит, одобряет и ставит на доставку |
| `approve_send` | отправляет последний показанный актуальный черновик |
| `start_mission` | сохраняет поручение по выбранному клиенту |
| `stop_mission` | останавливает поручение |
| `mission_status` | показывает одно поручение |
| `list_missions` | показывает активные поручения |
| `select_lead` | меняет активного клиента |
| `list_clients` | показывает доступных клиентов |
| `overview` | краткая сводка по системе и сделкам |
| `question` | отвечает по истории конкретной сделки |
| `collect_spec` | готовит следующий вопрос для сбора ТЗ |
| `design_concept` | запускает подготовку дизайн-концепций |
| `clarify` | задаёт владельцу недостающий уточняющий вопрос |

AI обязан вернуть один из этих вариантов с recipient, instruction, confidence и
кратким пересказом. Неизвестный инструмент или произвольное действие он создать
не может.

## Память владельца

`owner_agent_sessions` хранит:

- активный `lead_id`;
- последний показанный `draft_id`;
- незавершённый intent и вопрос бота;
- варианты выбора, если имя неоднозначно;
- время обновления.

Поэтому после вопроса «Кому написать?» можно ответить «Олегу» или номером из
списка. Незавершённый контекст имеет TTL около часа, после чего не должен влиять
на новую команду.

## Поиск и выбор клиента

Получатель ищется по подтверждённому имени, FL.ru login, Telegram username,
автору сообщений и внешним ID каналов. Русские падежные окончания нормализуются
для поиска. Если найдено несколько совпадений, бот показывает нумерованный
список; молча выбирать первого запрещено.

Местоимения «ему», «ей», «клиенту» используют активный lead. Если активного
клиента нет, бот просит выбрать его. Перед отправкой identity сверяется ещё раз.

## Разница между «напиши» и «отправь»

- «Напиши Олегу про сроки» — создать черновик, ничего не отправлять.
- «Отправь Олегу …» — создать текст, одобрить и поставить на доставку.
- «Отправь» — одобрить последний показанный черновик.

Условные команды «отправь потом», «когда ответит», «если согласится» не дают
системе права самостоятельно выбрать момент. Для них нужен явный новый приказ.

Перед отправкой проверяются recipient, статус draft, content hash и
`last_inbound_message_id`. Если клиент написал после генерации, черновик
становится `stale` и должен быть подготовлен заново.

## Входящее сообщение клиента

Telegram webhook:

1. проверяет secret token webhook;
2. определяет, это владелец или Business-клиент;
3. находит существующий lead или создаёт Telegram lead;
4. связывает Telegram identity с канонической сделкой;
5. сохраняет сообщение идемпотентно;
6. обновляет `last_inbound_message_id` и стадию;
7. помечает старые черновики устаревшими;
8. сохраняет контекст для следующей команды владельца.

В production включён `TELEGRAM_ON_DEMAND_ONLY=true`. Поэтому без адресной миссии
входящее сохраняется, но дальнейшее действие запускает владелец. Активная миссия
для конкретного клиента является узким исключением: только новое live-сообщение
этого клиента ставится в очередь, после чего действуют все stop-гейты и лимит ходов.

Дополнительно действует прогрессивный gate: даже после отключения on-demand
конкретный безопасный класс должен набрать порог ручных одобрений без правок.
Деньги, сроки, договор, гарантии, доступы, негатив и вопрос об ИИ не открываются
никогда. Плановые follow-up сначала создаются в «На проверку».

## Политика хорошего ответа

Агент объединяет до шести последовательных входящих сообщений после последнего
ответа. Он отвечает на пакет целиком, а не только на последнюю строку.

Обычная реплика:

- до 500 знаков, кроме подтверждения большого ТЗ;
- максимум один вопрос;
- максимум семь discovery-вопросов за разговор;
- сначала полезный вывод, затем вопрос;
- без пересказа слов клиента как единственной «ценности»;
- FL.ru — деловито и компактно;
- Telegram — естественнее, но без фамильярности.

Стоп-темы: цена, бюджет, скидка, сроки, договор, предоплата, гарантии, NDA,
доступы и ключи, просьба о человеке/созвоне, негатив, вопрос «вы бот?», опасные
условия и низкая уверенность. В этих случаях агент не выдумывает обязательства,
а сообщает срок личного ответа владельца.

## Переход FL.ru → Telegram

Когда есть предметный интерес, система создаёт одноразовый код `FS-XXXXXX` в
`conversation_handoffs`. Клиент присылает код Telegram-боту, после чего:

- код проверяется по статусу и сроку действия;
- Telegram peer добавляется в `lead_channels` того же lead;
- история FL.ru остаётся доступной агенту;
- новые требования продолжают обновлять ту же сделку;
- повторное использование кода блокируется.

## Доставка через Business API

После одобрения создаётся `outbound_deliveries` с idempotency key. Business API
делает одну внешнюю попытку. Результаты:

- `sent` — Telegram подтвердил доставку;
- `failed` или `blocked` — известная ошибка;
- `send_unknown` — соединение оборвалось, факт доставки неизвестен;
- `BUSINESS_PEER_INVALID` — допускается передача owner-session bridge.

При `send_unknown` автоматического повтора нет.

## Fallback через аккаунт владельца

`ops/sales_telegram_userbot.py` не входит в Telegram сам. Он работает с уже
существующим MTProto sender через общую SQLite outbox:

1. выбирает только delivery с `BUSINESS_PEER_INVALID`;
2. сверяет одобренный content hash;
3. проверяет дневной лимит;
4. кладёт одну запись в `mtproto_outbox`;
5. ожидает результат существующего sender;
6. атомарно обновляет delivery, draft, message и activity;
7. API сообщает владельцу финальный результат.

Повторная постановка той же delivery невозможна по первичному ключу. Bridge
опционален и включается только `SALES_USERBOT_ENABLED=true`.

## Миссии

Команды вроде «веди Олега до ТЗ» создают `lead_missions` с инструкцией,
необязательным deadline и лимитом ходов. Можно посмотреть статус или остановить
миссию.

При `TELEGRAM_ON_DEMAND_ONLY=true` активная миссия превращает только новое
live-сообщение выбранного клиента в один автоматический ход. Историческая
MTProto-синхронизация ответы не запускает. Цена, сроки, договор, гарантии,
обязательства, нездоровый коннектор, истёкший deadline и исчерпанный лимит
останавливают автоматический ответ и возвращают решение владельцу.

## Поддержанные и неподдержанные сообщения

Надёжно поддерживается обычный текст. Голосовые могут поступить через отдельную
MTProto-расшифровку. Фото, документы, подписи к media, редактирования и удаления
не следует считать полноценно обработанными без отдельной целевой проверки.
Owner-session fallback отправляет текст личным пользователям, не media и не
группам.

## Примеры безопасных команд

```text
Покажи клиентов
Работаем с Владимиром
Что нового по Владимиру за неделю?
Напиши Владимиру, что я проверю OAuth callback и вернусь завтра
Отправь Владимиру: проверил callback, адрес готов
Собери ТЗ
Сгенерируй 4 концепции по https://example.com
Стоп по Владимиру
```

После любой команды отправки владелец должен получить отдельный окончательный
результат: отправлено, не отправлено или статус неизвестен.
